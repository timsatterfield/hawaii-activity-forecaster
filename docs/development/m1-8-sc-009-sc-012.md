## How the inputs were authored

Application and driver inputs were derived from the release `recovery` (SC-009) and
`favorable` (SC-012) environments. The pilot already exercised both. The
derivation does the following:

- Restricts them to the 08:00–11:00 HST window and the scenario's activity.
- Prefixes every fixture, finding, operation, rule and premise ID.
- Renames the zone.
- Keeps only the operations each scenario's allowlist can reach.

It also applies the pack's conventions: findings cover exactly the scenario window,
and premise rationales are marked SYNTHETIC. The catalog is byte-identical to the
release catalog. `expected.json` files were written by hand from acceptance §§SC-009
and SC-012 and the declared inputs, never from application output. Preflight,
including the allowlist checks, passes for all four scenarios.

### SC-009

"Where should I swim tomorrow morning?" Five supported swimming candidates.

- **Weather.** Alerts and wind succeed.
- **Primary marine.** The NWS_MARINE batch **times out**. No retry is offered, so
  retry capacity remains, as the spec's conditions require.
- **Fallbacks.** The approved HWT_SURF and SNORKEL_STORE fallbacks succeed.
- **Other checks.** Visibility and all five water checks succeed.

Premises declare complete non-hazard and positive support for all five, but they

assertions require:

- The recorded `SOURCE_TIMEOUT`.
- Both `FALLBACK_INITIATED` and `TOOL_COMPLETED` events.
- Accepted fallback findings with their original coverage and timestamps.
- All five candidates ELIGIBLE/SUFFICIENT/FAVORABLE.
- One to three recommendations, all sufficient and favorable, with no ranking claimed.
- No exclusion, abstention or failure.
- Tool calls within limits. An offline run uses 11 of 12.

## SC-012 blocker: model input bound — resolved by profile 0.3

The follow-up's `normalize_request` body carries the inherited request (area,
experience level, calm-water preference). On the reviewed OpenAI profile
`m1-saturday-runtime-0.2` it measures **8,495 bytes** against the fixed
**8,000-byte** `INPUT_LIMIT`. It is rejected before dispatch with
`MODEL_HTTP_INPUT_INVALID`, live or offline. The spec's wording cannot be
shortened, because the harness must submit the natural-language requests verbatim.

| Request | OpenAI 0.2 | Ollama 0.5 |
|---|---|---|
| Pilot initial "…snorkel tomorrow morning near Kihei?" | 7,072 | 8,006 |
| Pilot follow-up "Actually near Napili instead." | 7,888 | — |
| SC-012 initial | 7,590 | 8,524 |
| SC-012 follow-up | **8,495** | — |

The bound is already close: the pilot follow-up passed with only 112 bytes to spare.

Evidence, from `tests/test_agent_scenarios.py`, with SC-012 copied as ACTIVE into a
temporary directory:

- **Current bound.** Step 1 passes and step 2 fails before dispatch.
- **12,000-byte bound**, patched in the test only. All **83 mandatory assertions
  pass** offline.

Options considered:

1. **New profile version** (e.g. `m1-saturday-runtime-0.3`) with a larger input
   bound, such as 12,000 bytes.
   - It also clears the Ollama preferred-area `xfail` if applied to the local
     profile.
   - The per-call cost reservation and provider pricing must be revalidated, since
     `INPUT_LIMIT` also caps reported input-token usage.
2. **Compact the `normalize_request` payload**, its prompt and schema, within the
   current bound. This is also a profile change, and the margin stays thin.
3. **Keep SC-012 BLOCKED** until a later model-profile batch.

**Owner decision (2026-11-19): option 1, a 12,000-byte bound.** It is implemented
as a new profile, `m1-saturday-runtime-0.3`, now used by `haf.release.example.toml`:

| | 0.2 (unchanged) | 0.3 |
|---|---|---|
| Prompts, schemas, template versions | `release-0.2` | Identical (`release-0.2`, same digests) |
| Input bound: prompt bytes, HTTP body and reported input-token cap | 8,000 | **12,000** |
| Reserve per dispatched call | 2,500 µUSD | **2,600 µUSD** |

The reserve had to rise, because 12,000 input tokens × $0.125/M (cache-write rate)
plus 2,048 output tokens × $0.50/M comes to 2,524 µUSD, more than the old 2,500.
Pricing is the 2026-11-19 check recorded in the
[integration notes](m1-integration-release.md). The conservative reserve is now
$0.0312 per 12-call investigation and $0.312 for ten investigations. These are
audit reservations, not billed amounts; measured pilot calls used about 1,000
input tokens.

The bound is now looked up per profile (`prompts.input_limit`). Profile 0.2 keeps
its 8,000 bound, so earlier traces still validate, and a test confirms 0.2 still
rejects the SC-012 follow-up. The Ollama profile is unchanged: its preferred-area
`xfail` remains, and a matching local-profile version would be a separate decision.
SC-012 is now ACTIVE.
