## SC-001

"Where should I snorkel tomorrow morning? I'm intermediate, prefer calm water, and
near Kihei." A, B and C have complete premises, and D's are omitted.

The assertions require:

- A, B and C each ELIGIBLE/FAVORABLE/SUFFICIENT, with supporting findings and no
  unresolved or disqualifying policies.
- Exactly three recommendations, one per beach (no D/E padding).
- No ranking claimed: `rank` is null for all recommendations.
- Accepted marine and water findings with their original coverage and window.
- The required trace events, all within limits.

**▲ Recorded deviation (owner decision, 2026-11-19).** The spec says the geographic
preference "favors A and B". Approved geographic matching is exact, by catalog
locality or region, with "no distance/nearby inference made"
(`validation/safety.py`). "Kihei" therefore matches only A. SC-001 asserts the
approved behavior: A `PREFERRED_AREA`, and B (Wailea) and C (Napili)
`OUTSIDE_PREFERRED_AREA`, with all three still eligible and recommended because the
preference is soft. Making B count as "near Kihei" would need an approved
nearby-area rule, which the design currently excludes.

## SC-003

"Where should I paddleboard tomorrow morning in South Maui?" "paddleboard" maps to
SUP, and "in South Maui" becomes a hard `LOCATION_RESTRICTION` on `SOUTH_MAUI`.
Only B supports SUP inside that area and has declared premises, including SUP's
mandatory wind fact.

The assertions require:

- The hard constraint.
- B ELIGIBLE and the only recommendation (`COUNT_EQUALS 1`, no padding).
- A and E assessed `UNSUPPORTED` (EL-006) and not recommended (CA-014).
- C and D (West Maui) not recommended (RR-008).
- Accepted evidence and the required events.

The assertions deliberately say nothing about whether C and D are assessed at all.
The spec does not specify it.

Offline, the run considers A/B/E, investigates only B, and uses 5 tool calls. The
offline test mock (`tests/release_samples.py`) now recognizes "paddleboard" and
"in South Maui". This is test-only. The application's own validator already
accepted both phrases.

## ▲ SC-002 deferral — design-change proposal for owner review

SC-002 ("Where should I swim tomorrow morning? I'd prefer somewhere near Kihei.")
needs Beach A to be **MIXED but explicitly permitted** for swimming. The approved
policy (harness design SH-OD-004, `harness/policy.py`) allows exactly one MIXED
permission: SNORKELING with `limitation_code: SYNTHETIC_POOR_VISIBILITY`, grounded
in HM-VIS-003. No swimming limitation code exists, so preflight would reject any
SC-002 fixture. The harness design's own coverage table flags this: "limitation
code still needs concrete authoring/review".

The proposal, for review only and with nothing implemented:

1. **Add one synthetic swimming limitation code**, for example
   `SYNTHETIC_MODERATE_SHOREBREAK`. Its permission would name the governing
   safety requirement and a disclosure, mirroring the visibility permission.
   - It needs an approved safety-policy basis stating when a swimming limitation
     is permitted rather than disqualifying.
   - The visibility permission relies on HM-VIS-003, and no equivalent swimming
     rule exists today. That rule is a safety-policy decision.
2. **Extend `MixedPermission` and premise validation** to accept that
   activity/code pair only, with the same "all conditions or not permitted" rule
   the visibility case uses.
3. **Author SC-002** with A MIXED/SUFFICIENT/ELIGIBLE (`PREFERRED_AREA`) and C
   FAVORABLE/SUFFICIENT/ELIGIBLE (`OUTSIDE_PREFERRED_AREA`). The assertions would
   require MIXED disclosure and no drive-time claims.
   - The spec's "C should be preferred under the synthetic comparison criteria"
     also needs checking against the result ordering, since recommendations
     currently carry no rank. It may need an assertion on grouping rather than
     order.

Until a safety-policy basis is approved, SC-002 stays unregistered rather than
registered with an invented permission.

The same request text passed live as SC-012 step 1, so this is the intermittent
normalization behavior seen in SC-004 #1, not a fixture fault.

**Diagnostic gap found and fixed.** `REQUEST_PROPOSAL_INVALID` is the generic
catch-all. `validate_request` caught `ValueError`, which `RequestValidationError`
subclasses, so every specific rejection collapsed into the catch-all before it
could be classified. It now re-raises the specific error unchanged. The request is
still rejected, but the next live failure will record a code such as
`REQUEST_SPAN_MISSING` or `REQUEST_CHANGE_UNSUPPORTED`. A regression test, which
fails without the fix, covers this. This trace predates the fix, so its exact rule
remains unknown.

**Field names added.** The rejection did not say which field lacked its span. The
four field-specific validator rejections now carry the closed request field name,
recorded as `field` on the rejected request-interpretation event. `field` is already
an approved trace key. Names come from `VALUE_FIELDS` only, never values, spans or
text, and the validator rejects anything else. SC-001 #2 predates this addition.

**Assessment.** SC-001's request ("…intermediate, prefer calm water, and near Kihei")
is the longest normalization case. Both failures were span-citation rejections,
while the identical text passed once as SC-012 step 1. The validator is doing its
job: it refuses values the model did not ground in the request. The likely fix is
prompt guidance in a new profile version, for example requiring a span for every
changed field and citing the whole clause ("I'm intermediate", "prefer calm water",
"near Kihei"). That is a model-profile decision for the owner. Relaxing the
validator would weaken grounding and is not proposed.

## Model profile 0.4 (owner decision, 2026-11-19)

Every live failure on profile 0.3 was a rejected `normalize_request` proposal:
SC-001 had span rejections, and SC-003 proposed `preferred_area` for "in South
Maui". `m1-saturday-runtime-0.4` changes only that prompt (template
`normalize_request-release-0.3`). It appends guidance that mirrors the trusted clause
rules in `interpretation/clauses.py`:

- `near`, `prefer`, `prefer near` and `ideally` set `preferred_area` only.
- `in`, `only` and `must stay in` before a region or locality are a hard
  `LOCATION_RESTRICTION`, never also `preferred_area`. `at` a beach is a BEACH
  restriction.
- Every changed field cites a span covering its whole phrase: the activity word,
  "tomorrow", the daypart word, the experience word, "prefer calm water" including
  "prefer", and the full location clause with its preposition.

| | 0.3 | 0.4 |
|---|---|---|
| Coordinator, Weather and Ocean prompts | `release-0.2` | Identical |
| `normalize_request` prompt | `release-0.2` | `release-0.3` (0.3 text plus the guidance above) |
| Input bound and reserve | 12,000 bytes, 2,600 µUSD | Identical |

The request validator is unchanged and stays the authority, so the guidance cannot
loosen grounding. `haf.release.example.toml` now uses 0.4. Profiles 0.2 and 0.3 are
unchanged, and all 14 existing pilot and acceptance traces still validate.
Offline, the largest 0.4 normalization request is 9,062 bytes (SC-012's follow-up),
within the bound.

While adding 0.4, a test caught a regression before it shipped: two name-based
profile sets in `prompts.py` would have dropped 0.3 once `SATURDAY_PROFILE` began
naming 0.4. Both now list 0.3 explicitly, and `test_release_profile.py` pins 0.3 to
0.2's prompts and limits 0.4 to the normalize change.

**Live results on 0.4:** SC-003 passed (attempt #2) after failing on 0.3, and SC-001
passed (attempt #4) after two span-rejection failures on 0.3. That is 2 of 2 on 0.4,
against 1 of 4 on 0.3 for these two requests. These are early observations, not a
measured reliability rate.
